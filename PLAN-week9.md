# Week 9 plan: what are the remaining "wrong result" errors? (error analysis, no training)

**Status: APPROVED 2026-11-20. Done 2026-11-20: schema-link + join 45%, gold issues 15%; spot check 17/20.**

## Why

The released configuration (v2-900, rows, repair, grounding) still fails 391 of 1,034 Spider dev
questions on our metric. **318 of them are "wrong result"**: the SQL runs but returns the wrong answer.
Weeks 5–8 worked on the smaller classes (execution errors, literals, `no such column`). Two training
attempts (weeks 5 and 8) gave null results. The largest error class has never been looked at
systematically.

The next experiment should be chosen from evidence, not guessed. This week only measures: which kinds
of mistakes make up the wrong results, and how many are not the model's fault (a buggy or ambiguous
gold query).

## Question

**Among wrong-result failures of the released configuration, what is the share of each error type,
and which type is both large and plausibly fixable?**

## Method (fixed in advance)

**Population:** the 301 questions where the released configuration
(`baseline_..._v2-checkpoint-900_repair_ground_rows3`) gives a running but wrong answer **and** the
official metric also scores it wrong. The 17 that only our metric marks wrong are excluded, since the
two metrics disagree on them.

**Sample:** 100 questions, drawn with a fixed seed (3407), stratified by official hardness in
proportion to the population (medium 117, extra 86, hard 70, easy 28 → about 39 / 29 / 23 / 9).

**Material per question** (generated by a script, so labelling sees the same view each time):
the question, the schema with example rows (the model's prompt), the gold SQL and the predicted SQL,
and the first 5 rows and row count of both results.

**Taxonomy** (fixed now; one primary label, at most one secondary):

| Label | Meaning |
|---|---|
| `schema-link` | wrong table or column for a concept in the question |
| `join` | wrong or missing join path, or a join that duplicates rows |
| `condition` | missing, extra or wrong `WHERE` / `HAVING` condition (not a literal issue) |
| `literal` | right condition, wrong value or value format |
| `aggregation` | wrong aggregate, `GROUP BY`, `DISTINCT` or count semantics |
| `order-limit` | wrong `ORDER BY` direction or column, a missing `LIMIT`, or tie handling |
| `nesting-setop` | wrong subquery, `INTERSECT` / `EXCEPT` / `UNION`, or `NOT IN` logic |
| `output-shape` | right rows, wrong columns: extra, missing or reordered columns |
| `gold-issue` | the gold query is wrong, or the question is ambiguous and the prediction is a valid reading |
| `other` | none of the above (described in a note) |

**Labelling:** I label all 100 with a short note each. **You check 20 of them** (random, seed fixed),
which gives a simple agreement rate. If agreement is below 15 / 20, the taxonomy is discussed before
anything is concluded.

**Output:** `results/error_analysis_wrong_result.md` (shares with counts, by hardness, examples per
label) and `results/error_analysis_labels.jsonl` (one labelled row per question).

## What the result would point to (stated in advance, not decided here)

| If the largest fixable share is | Candidate next experiment |
|---|---|
| `schema-link` or `join` | schema pruning, or foreign-key hints in the prompt |
| `output-shape` | a prompt instruction about returned columns, or checking whether the official metric already forgives it |
| `literal` | extending grounding (numbers, dates) |
| `aggregation`, `condition` or `nesting-setop` | self-consistency (sample several answers, vote by execution result), with no training |
| `gold-issue` is large (e.g. >25%) | the measured ceiling on Spider is lower than it looks; a second benchmark (BIRD) becomes more useful than more Spider work |

The next week's plan is then written separately and approved as usual.

## Risks

- **Labeller bias.** I wrote the model's pipeline, and the labels are judgements. Your 20-row check is
  the guard; disagreements are reported, not hidden.
- **Overlapping labels.** Many errors have more than one cause. The primary label is "the first thing
  that would have to change for the answer to be right".
- **n=100.** Shares have wide intervals (±~10 points for a 30% share). Enough to find the largest class,
  not to rank close ones.
